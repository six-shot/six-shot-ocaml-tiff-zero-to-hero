How to learn from this guide

You learn a language by writing it, getting it wrong, and fixing it yourself. Reading answers, from this page or from an AI tool, feels like progress but doesn't stick. These habits will make the guide work for you:

What OCaml is

OCaml is a programming language from France (INRIA), first released in 1996. It's used for compilers, financial trading systems (Jane Street), the Tezos blockchain, static analysers, and libraries like ocaml-tiff. Three ideas describe it:

1. Functional first

In OCaml you mostly build programs out of functions that take values and return new values, instead of changing variables step by step. A name made with let never changes. If you want a different value, you make a new one.

(* JavaScript style: change a variable *)
(* let total = 0; for (x of xs) total += x; *)

(* OCaml style: describe the result *)
let total = List.fold_left ( + ) 0 [ 8; 8; 8 ]   (* 24 *)

Functions are ordinary values: you can pass them to other functions, return them, and store them. OCaml still has loops and mutable variables when you need speed (Level 6), but they're the exception.

2. Strong static types, mostly invisible

Every value has a type, and the compiler checks all of them before the program runs. You rarely write types yourself, because OCaml infers them. If you add an int to a float, or forget to handle a case, the program doesn't compile. A lot of bugs that would crash a JavaScript or Python program at runtime are caught here instead.

There is no null and no automatic conversion between number types. That feels strict at first, and it's the main reason OCaml code tends to work once it compiles.

3. Compiled to fast native code

The compiler turns your .ml files into a native program, as C or Rust does. You can also use utop, an interactive prompt, to try one line at a time. This guide uses utop for every “Try it” box.

TIFF in one picture

A TIFF file is a header, then one or more directories (IFDs) describing images, then the pixel data cut into strips. The directory says where everything else is, using byte offsets.

        │  4D 4D   "MM" = big-endian    │
        │  00 2A   magic 42 = TIFF      │
        │  00 00 00 08  first IFD → 8 ──┼──┐
byte 8  ├───────────────────────────────┤  │
        │ IFD (image file directory) ◄──┼──┘
        │  00 0C   12 entries follow    │
        │  ┌ entry: tag | type | count | value or offset
        │  │ 256 ImageWidth    = 256    │
        │  │ 257 ImageLength   = 128    │
        │  │ 258 BitsPerSample = 8      │
        │  │ 259 Compression   = 5 (LZW)│

        │  │ 278 RowsPerStrip  = 64     │  │
        │  │ 279 StripByteCounts → …    │  │
        │  └ 317 Predictor     = 2      │  │
        │  next IFD offset = 0 (none)   │  │
        ├───────────────────────────────┤  │

Level 1 src/endian.ml

let, functions and types you never write

let names a value. A function is just a value that takes arguments. Arguments are separated by spaces, not commas, and OCaml infers every type. Here is the first function in endian.ml:

src/endian.ml
type endianness = Big | Little

let uint16 ?(offset = 0) endian buf =
  match endian with
  | Big -> Cstruct.BE.get_uint16 buf offset
  | Little -> Cstruct.LE.get_uint16 buf offset
  • ?(offset = 0) is an optional argument with a default. Callers write Endian.uint16 ~offset:2 e buf or leave it out.
  • There is no return. The last expression is the result.
  • The type, worked out for you, is ?offset:int -> endianness -> Cstruct.t -> int. Read each -> as “then”.

Composition with |>

let set_float32 ?(offset = 0) endian buf value =
  Int32.bits_of_float value |> set_uint32 ~offset endian buf

x |> f means f x. It lets you read left to right: “turn the float into bits, then write them”. The tests use the same idea: (Tiff.ifd tiff |> Tiff.Ifd.predictor).

Integers are not floats

+ - * / work on int only. Floats use +. -. *. /.. There's no automatic conversion: you call float_of_int or Int64.to_int yourself. That's why ifd.ml is full of Int64.to_int.

Try it
let add a b = a + b;;        (* val add : int -> int -> int *)
let add5 = add 5;;           (* partial application: a new function *)
add5 10;;                     (* 15 *)

Level 2 src/ifd.ml · tag, compression, predictor

Variants and pattern matching

A variant type lists every possible case. A case can carry data. This is how the library turns TIFF's magic numbers into readable names:

src/ifd.ml:366
type predictor = No_predictor | HorizontalDifferencing | Unknown of int

let predictor_of_int = function
  | 1 -> No_predictor
  | 2 -> HorizontalDifferencing
  | i -> Unknown i
  • function is shorthand for fun x -> match x with.
  • Unknown of int keeps the raw number, so a file with predictor 3 isn't lost. It ends up as Unknown 3.
  • The last pattern i catches everything else and binds it to a name.

The compiler checks that a match covers every case. In apply_predictor (tiff.ml:258) all three predictor cases are handled. Delete the Ifd.Unknown n line and dune build warns that the match is non-exhaustive. That warning is the reason OCaml code is hard to break by accident.

Matching on several values at once

src/tiff.ml:113 (get_plane)
match (planar_configuration, plane) with
| Planar, Some p -> p
| Planar, None -> invalid_arg "Must specify plane for data read"
| Chunky, None | Chunky, Some 0 -> 0
| Chunky, Some _ -> invalid_arg "Can not select plane on single plane TIFFs"
| Unknown _, _ -> invalid_arg "Unknown planar format TIFF"

Build a tuple, then match its shape. | between two patterns means “either”, and _ means “anything, I don't need it”.

Same constructor name in two types

Unknown appears in tag, predictor, sample_format, photometric_interpretation and planar_configuration. OCaml picks the right one from the expected type. When it can't tell, you qualify it: Ifd.Unknown n. So writing Horizontal instead of HorizontalDifferencing fails to compile: no constructor has that name.

Level 4 ifd.ml lookup · tiff.ml compute_data_offsets

Lists, higher-order functions and folds

A list is written [ 1; 2; 3 ] (semicolons, not commas). x :: rest puts x on the front, and @ joins two lists. Functions that take other functions do most of the work:

src/ifd.ml:465
let lookup e tag = List.find_opt (fun e -> e.tag = tag) e
let lookup_exn e tag = List.find (fun e -> e.tag = tag) e

fun e -> … is an anonymous function. The _opt version returns an option, while the _exn version raises Not_found. The standard library follows this naming everywhere.

fold_left: a loop with an accumulator

src/tiff.ml:368
let compute_data_offsets strip_bytecounts start_offset =
  let _, data_offsets =
    List.fold_left
      (fun (current_offset, acc) count ->
        (current_offset + count, current_offset :: acc))
      (start_offset, []) strip_bytecounts
  in
  List.rev data_offsets

The state is a pair: the running offset and the list built so far. Each strip adds its own start to the list and moves the offset on. Building with :: puts the list in reverse order, so List.rev fixes it at the end. You'll see this pattern all over OCaml code.

The same idea shows up in List.fold_left Int.add 0 bits_per_sample (tiff.ml:131), which is just a sum.

Try it
List.map (fun b -> b / 8) [8; 8; 8];;           (* [1; 1; 1] *)
List.init 3 (fun _ -> 16);;                      (* [16; 16; 16], see make at tiff.ml:510 *)
List.fold_left ( + ) 0 [8; 8; 8];;               (* 24 *)

Level 5 lzw.ml get_bits · tiff.ml all_ifds

Recursion, including the tail-recursive kind

A function that calls itself has to be declared with let rec. Here is the bit reader that LZW is built on:

src/lzw.ml
let rec get_bits bytedata offset count =
  match count with
  | 0 -> 0
  | n ->
      let byte = int_of_char (Cstruct.get_char bytedata (offset / 8)) in
      let bitoffset = offset mod 8 in
      let bit = (byte lsr (7 - bitoffset)) land 1 in
      (bit lsl (n - 1)) + get_bits bytedata (offset + 1) (n - 1)

It reads one bit, shifts it into place, and adds the rest. let … in introduces a local name for the expression that follows.

Walking a linked chain of IFDs

src/tiff.ml:392
let all_ifds first_ifd =
  let rec aux acc ifd =
    match Ifd.next_ifd ifd with
    | None -> acc
    | Some ifd' -> aux (ifd' :: acc) ifd'
  in
  aux [ first_ifd ] first_ifd |> List.rev |> Array.of_list

The recursive call to aux is the very last thing it does. That makes it a tail call, which OCaml turns into a loop, so no stack builds up. get_bits is not tail-recursive (it still has a + to do after the call), but it never goes deeper than 12.

The LZW decode function is one large tail-recursive inner that carries its state (input offset, output offset, code size, next code, previous string) as arguments instead of using variables. Read it once you're comfortable with this level.

Modules, interfaces and hidden types

Every file is a module. A matching .mli file is its interface: only what's listed there is visible to the outside. ifd.ml has 1,299 lines and ifd.mli has 268, so the rest is private.

src/ifd.mli

Modules inside files, and re-exporting

module Data = struct … end          (* tiff.ml:36, a sub-module *)

In tiff.mli, module Data : sig … end is the signature of the sub-module. Private is a convention: it's public so test_lzw.ml can reach Tiff.Private.Lzw.get_bits, and the name warns everyone else not to use it.

Level 8 file.ml · tiff_unix.ml · process_data callbacks

Functions as values, labels and callbacks

This is the library's best design idea. It never opens a file itself. It only asks for a function that reads bytes at an offset:

src/file.ml
type ro = file_offset:Optint.Int63.t -> Cstruct.t list -> unit

file_offset: in a type is a labelled argument, and callers must write ~file_offset:x. Unix and Eio each give back a function of this type:

src/unix/tiff_unix.ml
let of_fd fd : Tiff.File.ro =
 fun ~file_offset bufs ->
  let _ : int =
    preadv fd (Array.of_list bufs) file_offset in
  ()
src/eio/tiff_eio.ml
let with_open_in path fn =
  Eio.Path.with_open_in path @@ fun r ->
  let ro = Eio.File.pread_exact r in
  fn ro

f @@ x means f x, but it binds loosely, so @@ fun r -> … passes the whole rest of the block as a callback. The tests read like this: with_ro backend path @@ fun ro -> ….

Resource safety

Fun.protect ~finally:(fun () -> Unix.close fd) (fun () -> fn (of_fd fd))

This always closes the file, even if fn raises an exception. It works like try/finally.

One walker, two jobs

process_data takes three callbacks: ~on_strip ~on_value ~after_strip. read_data passes callbacks that decompress and fill the array, and write_data passes callbacks that copy from the array and write. It's the same loop for both, so reading and writing can't disagree about strip layout.

Labels also guard against mixing up arguments. That's why undo_horizontal_differencing takes ~width ~samples_per_pixel ~bytes_per_sample ~endian: four ints in a row are easy to swap, but four labelled ints aren't.

  let off = ref (Optint.Int63.to_int file_offset) in
  List.iter (fun b ->
    let n = Cstruct.length b in
    if !off + n > String.length s then raise End_of_file;

let predictor t =

The TIFF spec says a missing Predictor tag means 1 (none), and this code implements exactly that. samples_per_pixel and sample_format follow the same pattern.

Result and polymorphic variants

src/deflate.ml
match Zl.Higher.uncompress ~allocate ~refill ~flush input output with
| Ok () -> ()
| Error (`Msg err) -> failwith ("DEFLATE decompression error: " ^ err)

('a, 'e) result is Ok x | Error e, so the error is a value instead of an exception. A backtick name like `Msg is a polymorphic variant: a constructor you can use without declaring a type first. ^ joins two strings.

Formatted messages

Printf.sprintf "…%d…" n builds a string, and the compiler checks that %d gets an int. The \ at the end of a line inside a string continues it on the next line and drops the leading spaces. The bit-depth error message in apply_predictor uses that.

Bit operators

lsl and lsr shift left and right, asr shifts right keeping the sign, and land lor lxor are AND, OR and XOR. Here's how a signed 8-bit value is read:

src/tiff.ml:43
let read_int8_value buf buf_index _ =
  (Cstruct.get_uint8 buf buf_index lsl (Sys.int_size - 8))
  asr (Sys.int_size - 8)

It pushes the byte to the top of the native int, then uses an arithmetic shift to bring it back down so the sign bit spreads. So 0xFF becomes −1. OCaml ints are 63 bits on 64-bit machines (one bit is used by the runtime), which is why the code uses Sys.int_size instead of 64.

The predictor mask, (1 lsl (8 * bytes_per_sample)) - 1, gives 255 or 65535.

Flattening for tests

The test helper assert_equal_ba uses Bigarray.reshape_1 a size to view any N-D array as one long 1-D array without copying, then compares element by element. That way a failure reports the exact index.

Level 11 tiff.ml kind · get_repr · (type a b)

GADTs: types that follow the data

This is the hardest idea in the codebase. When you ask for Tiff.from_file Tiff.Uint16 ro, the array you get back has type (int, int16_unsigned_elt) Data.t. When you ask for Float32, you get a float array. The way the value you pass decides the type you get back is a GADT (generalised algebraic data type):

src/tiff.ml:9
type ('repr, 'kind) kind =
  | Uint8 : (int, Bigarray.int8_unsigned_elt) kind
  | Uint16 : (int, Bigarray.int16_unsigned_elt) kind
  | Float32 : (float, Bigarray.float32_elt) kind
  …

Each constructor fills in the type parameters itself. 'repr is the OCaml type you work with (int, float, int32), and 'kind is the storage type Bigarray uses.

Locally abstract types

src/tiff.ml:414
let get_repr (type repr kind) (t : (repr, kind) t) ifd plane :
    (repr, kind) Bigarray.kind
    * (Cstruct.t -> int -> Endian.endianness -> repr) * … =
  match (t.data_type, sample_format, bpp) with
  | Uint8, UnsignedInteger, 8 -> (Bigarray.int8_unsigned, Data.read_uint8_value, …)
  | Float32, IEEEFloatingPoint, 32 -> (Bigarray.float32, Data.read_float32_value, …)
  | typ, fmt, bpp -> Fmt.invalid_arg "datatype not correct for plane: …"

(type repr kind) names the type parameters so each branch can refine them. In the Uint8 branch the compiler knows repr = int, so returning an int reader type-checks. In the Float32 branch it knows repr = float. Without the annotation, the branches would have to agree on one type.

This is also why test_load_data_as_wrong_type_fails exists. If you ask for Int8 on a uint8 file, it falls through to the last case and raises.

Read bits_per_sample_of_kind (tiff.ml:336) and of_ba_kind (inside make), which go the other way: from a Bigarray kind to TIFF metadata.

Exercise

Why does pp_kind (tiff.ml:19) start with (type r k)? Remove it and read the compiler error.

Answer

Each constructor has different type parameters. To match on all of them in one function, the parameters must be locally abstract so each branch can refine them. Without it you get an error like “this pattern matches values of type (float, …) kind but a pattern was expected which matches values of type (int, …) kind”.

Testing with OUnit2

test/test_tiff.ml:679

Asserting well

let assert_equal_int = assert_equal ~printer:Int.to_string

Without ~printer, a failure only says “not equal”. With it, you see both values. That's why the tests have assert_equal_ba: plain assert_equal on two big arrays can't print them usefully.

test/dune runs the binary with -runner sequential because OUnit's default runner forks, and that breaks Eio.

Level 13 src/unix/tiff_unix.ml · lzw.ml Unsafe

Talking to C with external

external preadv : Unix.file_descr -> Cstruct.t array -> Optint.Int63.t -> int
  = "caml_tiff_preadv"

external declares an OCaml name for a C function. The C code lives in tiff_unix_stubs.c, and src/unix/dune compiles it through (foreign_stubs (language c) (names tiff_unix_stubs)). lzw.ml does the same with a runtime primitive, caml_blit_string_to_bigstring, marked [@@noalloc] to promise that the C side never allocates. That makes the call cheaper.

That's why Eio is optional in src/eio/dune ((optional)) while the core tiff library depends on neither. The core stays pure OCaml, and the I/O is plugged in from outside (Level 8).

Extra not used in ocaml-tiff, but everywhere else

A short note on functors

A functor is a function from modules to modules. You give it a module, and it builds a new module for you. The standard library's maps and sets are made this way. ocaml-tiff doesn't define any functors, but you'll meet them in almost every other OCaml project.

(* Map.Make needs a module with a type t and a compare function *)
module TagMap = Map.Make (struct
  type t = Tiff.Ifd.tag
  let compare = compare
end)

let names =
  TagMap.empty
  |> TagMap.add Tiff.Ifd.ImageWidth "width"
  |> TagMap.add Tiff.Ifd.Predictor "predictor"

let () = print_endline (TagMap.find Tiff.Ifd.Predictor names)   (* predictor *)

Map.Make is the functor. The struct … end is the module you pass in. TagMap is the new module it builds, with empty, add, find and the rest, all typed for tag keys.

Ready for more? Read the functors chapter in Real World OCaml, then look at how Eio or Irmin use them.

Hero every level in one call

Trace one read from end to end

Open the files side by side and follow Tiff.data tiff ro on an LZW file with a predictor, for example u16bit_rgb_lzw_predictor_be.tiff from the test data.

  1. Tiff_unix.with_open_in path @@ fun ro -> gives you a File.ro closure (L8).
  2. Tiff.from_file Tiff.Uint16 ro (tiff.ml:400) calls Ifd.read_header, which reads 16 bytes and matches "MM" to Big and magic 42 to Tiff (L2, L3).
  3. Ifd.v (ifd.ml:943) reads the entry count and then every 12-byte entry: tag, field type, count, and either an immediate value or an offset (L6, L10).
  4. all_ifds follows next_ifd until it hits 0 (L5).
  5. Tiff.data (tiff.ml:442) checks the cache with a when guard, picks a reader with the get_repr GADT (L3, L11), and calls Data.read_data.
  6. read_data creates a Genarray of [| h; w; 3 |] and hands three callbacks to process_data (L8).
  7. For each strip, on_strip reads the compressed bytes, then Lzw.decode runs, then apply_predictor, which matches HorizontalDifferencing and Chunky to get stride 3 and runs the loop from Level 6 with ~endian:Big (L2, L6).
  8. For each pixel and channel, on_value reads 2 bytes with Endian.uint16 and calls Genarray.set arr [| y; x; c |] (L1, L10).
  9. The test compares the result with the uncompressed u16bit.tiff using assert_equal_ba (L12).
